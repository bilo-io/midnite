# Phase 84 — Connected GitHub (repos, multi-repo projects & Projects v2)

> **Builds on** **[Phase 70](phase-70-google-github-sso.md)** (GitHub SSO — `SsoService`, `user_identities`, the device + redirect flows), **[Phase 13](phase-13-repos-first-class.md)** (the DB-backed repo registry and the `project.workDir → repo.path → default` cwd precedence), **[Phase 14](phase-14-workflows-connect.md)** (the AES-256-GCM credential vault + its `/oauth/:provider/*` flow for google/slack), **[Phase 37](phase-37-ai-code-review.md)** (`repos.ownerRepo`, the `gh`/PAT ladder in [`github-diff.ts`](../packages/gateway/src/tasks/lib/github-diff.ts), and the `pr_status` satellite-table pattern), and **[Phase 46](phase-46-inbound-integrations.md)** (the inbound GitHub webhook adapter).

> **Why now.** midnite touches GitHub in four unconnected places — a shared PAT for PR review, three workflow executors, inbound webhooks, and a client-side issue-prefill — but it has **no notion of *your* GitHub**. Signing in with GitHub tells us who you are and then throws the access token away, so Settings → Repos still makes you hand-type a name, a filesystem path and an `owner/repo` slug for every checkout. Meanwhile a project can only point at **one** `workDir`, and nothing links a midnite task to the GitHub Project board a team actually plans on. This phase makes GitHub a **connected account**: browse and import your real repos, let a project span several of them, and keep a linked GitHub Projects v2 item in step with the task.

> **Scope guardrails (CLAUDE.md).** New contracts live in `shared` — the repo/project/link shapes are the contract, never duplicated. Gateway layering holds: `controller → service → repository`, GraphQL and REST calls behind a service, no Drizzle outside `repos/`, `projects/` and the new `github/` repositories. `web` stays a pure HTTP/WS client. **The login SSO path is not touched** — see Theme A and §1. **Every path in this phase must work on a bare local install** (own gateway, own SQLite, no hosted anything, no client secret) — §11.
>
> **Out of scope:** cloning repos from the picker (we *match* existing checkouts — §2); escalating `GITHUB_DEFAULT_SCOPES` or editing the SSO callback (that surface belongs to in-flight **[Phase 75](phase-75-desktop-oauth.md)**); a GitHub App / installation tokens (§4); full two-way sync via inbound `projects_v2_item` webhooks (§5); migrating `task.repo` from a name string to a `repoId` FK; per-project repo-name uniqueness (the global unique index on `repos.name` stays); GitHub Enterprise Server (the SSRF guard in [`safe-webhook-delivery.ts`](../packages/gateway/src/lib/safe-webhook-delivery.ts) rejects private-network hosts); GitHub Projects **classic** (v1).

> Effort tags: **S** small · **M** medium · **L** large. Natural order: **A** (the connection) is load-bearing and runs first; **B** (repo discovery) proves it end-to-end; **C** + **D** are a pair (the join table is meaningless until cwd resolution respects it); **E** → **F** are the Projects v2 stack; **G** closes out.

## Current state (what exists to build on)

- **GitHub SSO discards the token.** [`sso.service.ts`](../packages/gateway/src/auth/sso.service.ts) requests `GITHUB_DEFAULT_SCOPES = 'read:user user:email'`, exchanges the code, calls `githubProfileFromToken(accessToken)` to fetch `/user` + `/user/emails`, and lets the token go out of scope. `SsoProfile` has no token field; `sso_auth_state` carries only short-TTL nonce/code rows and says so in a comment. **Nothing in the repo stores a GitHub token per user.**
- **The credential vault has the machinery but not the ownership.** [`oauth.service.ts`](../packages/gateway/src/workflows/credentials/oauth.service.ts) already does encrypted-state CSRF, a token exchange, and lazy refresh-on-`resolve()`; [`crypto.service.ts`](../packages/gateway/src/crypto/crypto.service.ts) gives fail-closed AES-256-GCM (`v1:<base64(iv|tag|ct)>`, key from `MIDNITE_SECRET_KEY`). But `workflow_credentials` is a **flat global bag** — no `userId`, no `teamId`, and `WorkflowCredentialsRepository.list()` has no scope predicate. `OAUTH_PROVIDERS = ['google','slack']`; the provider branches are hard-coded `if google … else slack`, not a strategy table. The existing `type: 'github'` variant is an opaque PAT (`{ token, enterpriseUrl? }`) with no `accessToken/refreshToken/expiresAt/scope`.
- **Token lookup is first-match-wins.** `pr-review.service.ts`'s `githubToken()` does `list().find(c => c.type === 'github')` — introducing per-user tokens would silently hand PR review whichever row sorts first.
- **Settings → Repos already exists and is fully manual.** [`repos-view.tsx`](../packages/web/app/(main)/settings/repos/repos-view.tsx) has i18n'd CRUD over `getRepos`/`createRepo`/`updateRepo`/`deleteRepo` plus a `GithubWebhookSection`. Every field is typed by hand. Sidebar entry at [`settings-sidebar.tsx`](../packages/web/app/(main)/settings/settings-sidebar.tsx).
- **Projects and repos are unlinked.** `grep repoId` across `shared` + `gateway` returns **zero hits**. `projects.workDir` is a single nullable TEXT column; "is this a repo?" is an inferred git check surfaced by [`project-repo-status.tsx`](../packages/web/components/projects/project-repo-status.tsx). `repos.name` is a `uniqueIndex`, so name→path is global and 1:1. `config.repos` is a **first-boot seed only** — the DB is authoritative after.
- **cwd resolution is already subtly wrong.** [`resolve-cwd.ts`](../packages/gateway/src/terminal/lib/resolve-cwd.ts)'s `pickSessionCwd()` orders `project.workDir → repo.path → agents default → process.cwd()`, called from `TerminalService.resolveCwd(sessionId)` (three spawn paths). So **whenever a project has a `workDir`, `task.repo` is ignored** — a task on repo B inside a project pointed at repo A spawns in the wrong tree today. Separately, [`agent-runner.service.ts`](../packages/gateway/src/pool/agent-runner.service.ts)'s `resolveChecksForRepo()` resolves its own cwd from `task.repo` alone and ignores `project.workDir` entirely.
- **No GraphQL client exists anywhere.** GitHub Projects v2 is GraphQL-only, so this phase introduces the first one.
- **`pr_status` is the right precedent for synced remote state** — a URL on the task, a satellite row holding fetched remote state, a poller that upserts and emits on change ([`pr-status.service.ts`](../packages/gateway/src/tasks/pr-status.service.ts)). `task_links` (URL-keyed, no external id, no uniqueness) is too thin for a real link; `user_identities`' `uniqueIndex(provider, providerUserId)` is the uniqueness shape to copy.
- **Neither dispatch seam fits a GraphQL mutation.** A `NotificationChannel` only sees a `Notification`, not the task. Outbound webhooks POST a formatted body to a URL and the `webhooks` table has **no config column**, so there is nowhere to store a target project id. `TaskEventBus` is the emit point to subscribe to instead.

## Theme A — Per-user GitHub connection — **M**

An explicit "Connect GitHub" that yields a **per-user** OAuth token, built on the vault's machinery but deliberately **outside** the login SSO path so it can't collide with in-flight Phase 75 (§1). **The connect flow must work on a bare local install** — device flow first, secretless by default (§11).

- [ ] **Add a `github-oauth` variant** to `WorkflowCredentialDataSchema` in [`workflow-credential.ts`](../packages/shared/src/workflow-credential.ts) — `{ type: 'github-oauth', accessToken, refreshToken?, expiresAt?, scope }` — and `'github'` to `OAUTH_PROVIDERS`. The existing opaque `type: 'github'` PAT variant stays untouched and keeps working.
- [ ] **Give credentials an owner** — `user_id` + `team_id` columns on `workflow_credentials` (migration, §7), a scoped `listForUser(userId)` / `findForUser(userId, type)` on the repository following [`team-scope.ts`](../packages/gateway/src/db/team-scope.ts), and null-owner rows treated as shared (so today's PAT keeps resolving).
- [ ] **Refactor the provider branches into a strategy table** — `buildAuthorizationUrl` / `handleCallback` currently `if google … else slack`; replace with a `provider → { authUrl, tokenUrl, scopes, parseToken, grant: 'redirect' | 'device' }` map so GitHub is an entry, not a third branch. Behaviour-preserving for google + slack (their specs run unedited, both stay `redirect`).
- [ ] **Secretless device-flow connect as the default path (§11)** — the vault's redirect flow is **secret-required**: [`oauth.service.ts`](../packages/gateway/src/workflows/credentials/oauth.service.ts) throws `OAuth client secret env var "…" is not set` before it builds an authorization URL, and it needs a callback GitHub can reach. A bare local install has neither, so GitHub connect gets a **device grant** modelled on [`sso.service.ts`](../packages/gateway/src/auth/sso.service.ts)'s `startDeviceAuth`/poll pair — `POST /oauth/github/device` (returns `user_code` + `verification_uri`, keeps the provider `device_code` server-side behind an opaque handle) and a poll endpoint that lands the `github-oauth` credential. **No client secret, no callback URL, no hosted gateway.**
- [ ] **A second built-in device client id** — `DEFAULT_GITHUB_CONNECT_CLIENT_ID`, a shipped OAuth App with **Enable Device Flow** ticked and `repo project read:org` requested, resolved exactly like the login one (`config.gateway.auth.sso?.github?.clientId ?? DEFAULT_…`) so an operator can substitute their own app without touching code. Distinct from `DEFAULT_GITHUB_DEVICE_CLIENT_ID` — the login app's narrow scopes must not widen (§1).
- [ ] **Redirect grant stays as the hosted opt-in** — when an operator has configured a connect `clientId` + `clientSecretEnv`, prefer the redirect flow (fewer clicks, no code typing); otherwise fall back to device. One resolution helper, unit-tested both ways, so the choice is data not branching in the controller.
- [ ] **Connect-flow parity with login on the device path** — reuse the login flow's hardening: opaque handle instead of the provider `device_code`, short-TTL state, `slow_down`/`expired_token`/`access_denied` handled as first-class outcomes, and the poll endpoint authenticated as the acting user (the credential is per-user, §8).
- [ ] **Request `repo project read:org`** for the connect flow — private repos, org repos, and read/write on Projects v2 in one honest consent screen (§3). Scopes overridable per-operator; the granted `scope` string is persisted so the UI can show what was actually granted. Device and redirect grants request the **same** scope string, so which grant an install uses is invisible downstream.
- [ ] **Refresh + disconnect** — extend `resolve()`'s lazy near-expiry refresh to `github-oauth` (GitHub OAuth tokens may be non-expiring; treat a missing `expiresAt` as "no refresh needed" rather than an error). Disconnect deletes the row **and** calls GitHub's token-revocation endpoint, so revoking in midnite actually revokes.
- [ ] **Fix `githubToken()`'s first-match-wins** in [`pr-review.service.ts`](../packages/gateway/src/tasks/pr-review.service.ts) — resolve in a defined order (the acting user's `github-oauth` → a shared `github` PAT → `gh` CLI → anonymous), with a regression spec pinning that a PAT-only install behaves exactly as today.

## Theme B — Repo discovery & checkout matching — **M** — ✅ DONE (PR #636, 2026-08-20)

Shipped **ahead of Theme A** (user decision): the per-user `github-oauth` connection
is not in yet, so discovery resolves whatever token the install already has, behind a
ladder built for A to slot into — `GithubTokenService`: (Theme A rung) → shared vault
`github` PAT → `gh auth token`. The connection reports which rung answered, so a
shared PAT never reads as *your* GitHub. Theme A adds its rung at the top and
repoints `pr-review.service.ts`'s first-match-wins `githubToken()` here.

- [x] **New `github/` gateway module** — `github.controller.ts` / `github.service.ts` / `lib/github-rest.ts`. `GET /github/repos` proxies `/user/repos` with pagination follow-through, returns the shared contract (name, `ownerRepo`, private, default branch, pushedAt, description), and short-TTL caches per user. 409 with a clear "not connected" code when the user has no `github-oauth` credential.
- [x] **Shared contracts** — `GithubRepoSchema`, `GithubConnectionSchema` (`{ connected, login, avatarUrl, scopes, connectedAt }`), and the import request/response shapes in [`packages/shared/src`](../packages/shared/src).
- [x] **Checkout matching** — a `lib/match-checkouts.ts` helper that walks configured roots one level deep, reads each `.git` remote URL, normalises it to `owner/repo` (ssh + https + `.git` suffix forms), and returns a map. New `github.checkoutRoots` config key (§6), defaulting to the parent of any already-registered `repos.path`. No cloning (§2).
- [x] **`GET /github/repos` annotates each repo** with `localPath` (matched checkout), `registeredRepoId` (already in the registry), or neither — so the picker can show *on disk at ~/Dev/x* · *already registered* · *not checked out*.
- [x] **Repo browser UI** in [`repos-view.tsx`](../packages/web/app/(main)/settings/repos/repos-view.tsx) — a "Browse my GitHub repos" action opening a searchable, org-filterable list with those three states; selecting a matched repo one-click-creates the registry row with `name`, `ownerRepo` and `path` prefilled. Unmatched repos are selectable but land with an empty path and an explicit "not checked out" affordance. i18n'd from the start (new `.tsx` files are born i18n-enforced).

**As built (decisions + review findings).** `.git/config` is **parsed** rather than
`git remote get-url` shelled out — one cheap read per candidate over a root that may
hold dozens of checkouts — and a `.git` **file** is followed through its `gitdir:`
pointer, so midnite's own `.worktrees/<branch>` layout resolves (`lastIndexOf`, not
`indexOf`: a path containing an outer `worktrees` segment otherwise truncates to a
config that doesn't exist). The **GitHub list is cached per user (5 min, `?refresh=1`
bypass); the checkout scan and registry lookup deliberately are not** — those are
exactly what changes while someone is on the page. An **un-cloned repo does not
import**: it prefills the create form and focuses the path field, rather than landing a
pathless row the board would fail to spawn in. The registry is read through the
caller's `TeamScope` (an unscoped read let one user's row disable another's import
button), **all three routes are gated at `member`** — reads included, because they
answer from an install-wide credential — and a rejected token re-casts to the
not-connected 409 while a genuine upstream failure maps to **502**, not 500.

## Theme C — Projects ↔ repos, many-to-many — **M** — ✅ DONE (PR #637, 2026-08-20)

- [x] **`project_repos` join table** (migration, §7) — `{ id (UUIDv7), project_id, repo_id, is_primary, created_at }`, unique on `(project_id, repo_id)`, indexed both ways. Plain intra-domain id refs, no cross-domain FKs (CLAUDE.md). `task.repo` **stays a name string** — no `repoId` migration this phase. Landed as **migration `0097`**; the one-primary invariant is maintained in the repository's transactions (first attach promotes, explicit attach demotes the incumbent, detaching the primary promotes the oldest survivor).
- [x] **Shared contracts** — extend `Project` with a derived `repos: ProjectRepo[]`, plus attach/detach/set-primary request shapes in [`project.ts`](../packages/shared/src/project.ts). Derived from the edges, never stored on the project row (mirroring how Phase 27 derives `dependsOn`) — and **`optional` like `dependsOn`**, not defaulted, which kept ~14 unrelated `Project` fixtures out of the diff. Hydrated on the **list** read too, via one batched `IN (...)` query beside the existing status counts.
- [x] **Service + endpoints** — `POST /projects/:id/repos`, `DELETE /projects/:id/repos/:repoId`, `PATCH /projects/:id/repos/:repoId` (primary flag) on the existing [`projects.controller.ts`](../packages/gateway/src/projects/projects.controller.ts); integrity rules in `projects.service.ts` (unknown repo → 404, duplicate → 409, exactly one primary, deleting a repo clears its edges).
- [x] **Backfill from `workDir`** — one edge per project whose `workDir` matches a registered `repos.path`, marked primary, so existing projects come out with the repo they already effectively had. **Runs at boot in TypeScript, not in the migration**: matching needs `realpath` (case-insensitive volumes + symlinked checkouts, per Theme D) and SQL cannot realpath. Idempotent — only ever touches projects with no edges.
- [x] **Project-detail Repos panel** — a card on the project page listing the project's repos with per-repo git status (reuse [`project-repo-status.tsx`](../packages/web/components/projects/project-repo-status.tsx) per row), add/remove, and a primary marker. Per-repo status landed as an **additive** `GET /projects/:id/repos/:repoId/status`; the existing `repo-status` route keeps working and now reports on the project's *effective* directory. **Also: the primary repo's path IS the project's effective working directory** (`workDir` stays the stored column and the fallback), so preview/build, git status and cwd resolution all move with the primary.
- [x] **Absorbs two bullets deferred out of Theme D** (they need this join to exist): scope `CwdResolverService`'s repo lookup to the project's repo set, and scope the task repo picker to the selected project's repos with an "any registered repo" escape hatch. Theme D's containment gate + `repo outside project workDir` warning are the interim stand-in — once the join lands, the mismatch is preventable rather than merely detectable.

## Theme D — cwd resolution correctness — **M** — ✅ DONE (PR #635 + #637, 2026-08-20)

The join table is inert until spawn honours it. This closes a bug that exists on `main` today.

- [x] **Invert the precedence in `pickSessionCwd()`** — `task.repo`'s resolved path now wins over `project.workDir`, which becomes the fallback for a task with no repo. Update the pinned Phase 13 B3 tests deliberately (the old ordering is the bug), and keep the `agents` default → `process.cwd()` tail intact. **Landed containment-gated (user decision):** the repo wins only when it resolves at or under the project's `workDir`; a repo pointing somewhere else still defers to the project rather than relocating the agent to an unrelated checkout, and the mismatch is logged as a `warn` naming both paths. Theme C is what removes that case at the source. (PR #635)
- [x] **Scope repo resolution to the project** — `CwdResolverService` resolves `task.repo` against the project's repo set when the task has a `projectId`, falling back to the global registry lookup (`repos.name` stays globally unique, so this is a refinement, not a behaviour break). Landed with Theme C, which supplied the join. (PR #637)
- [x] **Fix the second resolution path** — route both spawn and quality-gate checks through **one** shared resolver so an agent and its checks can never disagree about the directory. **The gate path was already routed** through `TerminalService.resolveCwd`; the real second resolver was `TasksService.runManualCheck`, which expanded `repo.path` itself and ignored the project entirely — so a manual "run checks" could validate a tree the agent had never worked in. All three now go through `CwdResolverService`, which also retired the `TerminalModule ↔ ProjectsModule` forwardRef. (PR #635)
- [x] **Scope the task repo picker** to the selected project's repos, with the rest of the registry still selectable below — an ordering, not a filter, so the escape hatch is intact. (PR #637)
- [x] **Regression specs** for the matrix: project+repo (inside and outside), project only, repo only, neither — table-driven on both the pure helper and the resolver service, plus call-through assertions pinning the spawn, gate and manual-check paths to the shared resolver. (PR #635)

## Theme F — Event-driven push & read-back — **M**

- [ ] **Subscribe to `TaskEventBus`** from the new `github/` module (the Phase 20 search module is the precedent for subscribing without editing `tasks.service`) — on `task.updated` where status changed and a link exists, push the mapped single-select option via GraphQL.
- [ ] **Idempotency + loop suppression** — record the last pushed option per link and skip no-op pushes; mark writes originating from a read-back so a poll can never trigger a push.
- [ ] **Failure handling** — push failures write `lastError` + a retry with backoff rather than throwing into the event path (the notification dispatcher's per-channel try/catch is the precedent: log, never break the caller). Surface the error on the task card, don't swallow it.
- [ ] **Read-back poller** — a `pr_status`-style interval that refreshes `status_option_name` + `item_url` for active links, emits `task.updated` on change so the board refreshes, and backs off on rate-limit. Read-back is **display-only** this phase — it never moves the midnite task (§5).
- [ ] **Delivery visibility** — a compact per-task sync log (last N pushes/reads with outcome) so a silent failure is diagnosable without gateway logs.

## Decisions / open questions

1. **Connect flow, not login scopes — resolved.** Per-user tokens come from a **separate vault-style `/oauth/github/*` connect flow**, auto-prompted after a GitHub sign-in (Theme G) so it reads as a continuation of login. Rationale: **[Phase 75](phase-75-desktop-oauth.md)** Theme C is editing `GET /auth/sso/:provider/callback` right now in a parallel session and restates Phase 70's "tokens are never persisted" decision; GitHub OAuth Apps grant scopes **app-wide at first authorization**, so bumping `GITHUB_DEFAULT_SCOPES` would force every existing user to re-consent; and `DEFAULT_GITHUB_DEVICE_CLIENT_ID` is a shipped public app that can't be re-scoped for self-hosters. Cost: a second OAuth app and one extra click. *Settled in brainstorm.*
2. **Match checkouts, don't clone — resolved.** The picker matches repos to checkouts already on disk by git remote URL and reports *on disk* / *registered* / *not checked out*. No clone root, no progress UI, no disk-space story. A later phase can add "clone the ones you don't have". *Settled in brainstorm.*
3. **Scopes: `repo project read:org` in one prompt — resolved.** A half-scoped connection that can browse repos but can't write back to a Project is worse than one honest consent screen. *Settled in brainstorm.* Open sub-question: whether to also request `read:project` separately for a read-only mode — recommendation **no**, `project` covers it.
4. **Two OAuth apps to document — but neither is the *user's* problem.** midnite ships both (login + connect) as built-in device-flow apps, so an end user registers nothing; a self-hoster who wants their own apps registers two, with different callbacks and scopes. Recommendation: document both in `docs/GITHUB.md`, lead with "you do not need to configure anything" (§11), and allow the connect flow to fall back to the login app's `clientId` **only** when an operator has explicitly widened the login scopes themselves — an escape hatch for single-app installs, off by default. Alternative worth revisiting later: one **GitHub App** with per-repo installation grants, which subsumes both and scopes better, at the cost of JWT signing and an install flow.
5. **Read-back is display-only.** Recommendation: keep it that way this phase. True two-way sync needs conflict rules ("who wins when both moved?") and inbound `projects_v2_item` webhooks through [`github.adapter.ts`](../packages/gateway/src/integrations/inbound/adapters/github.adapter.ts). Shipping display-only first means the UI never lies about direction, and the link table already has the columns two-way would need.
6. **Where `checkoutRoots` is configured.** Recommendation: a new `github.checkoutRoots` key in `midnite.json` (user config, not operator config — it's a path preference, not a secret), defaulting to the parent directories of already-registered `repos.path` values so a populated install needs no configuration at all. `config.repos` is only a first-boot seed and is the wrong place.
7. **Migration numbers `0097`–`0099` may be contested.** The highest on `main` is `0096_milestone_dependencies` and parallel branches claim numbers off the same base. Flag the exact numbers in the PR description so whichever lands second renumbers at rebase. Journal `when` values are hand-assigned round numbers — keep them **increasing**, or the migration silently skips on existing DBs.
8. **Per-user or per-user-per-team connection?** Recommendation: store both `user_id` and `team_id` but resolve on **`user_id`** alone this phase — one GitHub account per person, reused across their teams. The `team_id` column exists so a later phase can add team-shared connections without a migration.
9. **What happens to a Project item when its task is deleted?** Recommendation: **leave the GitHub item alone** and drop the link row, logging it. Deleting someone's board card as a side effect of a local delete is a blast-radius surprise; Phase 50's guardrail instinct applies.
10. **Should scopes become runtime-editable?** Because `gateway.auth` lives in the gitignored `.midnite/operator.json`, a scope change can't ship in a release — each operator must edit their own file. **[Phase 83](phase-83-admin-allowlist-management.md)** Theme A establishes the `effective = file ∪ db` pattern for exactly this problem. Recommendation: **not this phase** — take the code default plus an `operator.example.json` update and a `midnite doctor` check, and adopt the runtime pattern later if scope churn becomes real.
11. **Local installs are the primary target — the connect flow must be secretless (device grant) — resolved.** Real users install the packaged app and run their own gateway against their own SQLite; **there is no hosted gateway**. Two consequences, and the phase is built around both:
    - **Login must keep working untouched.** It already does the right thing: a device grant against the shipped `DEFAULT_GITHUB_DEVICE_CLIENT_ID` ([`sso.service.ts:45`](../packages/gateway/src/auth/sso.service.ts#L45)) with `read:user user:email` ([`sso.service.ts:35`](../packages/gateway/src/auth/sso.service.ts#L35)) — no secret, no callback, no configuration. Nothing in this phase edits `/auth/sso/*`, and §1's reasoning (OAuth Apps grant scopes app-wide at first authorization, so a scope bump forces mass re-consent) is *why* the connect flow is separate rather than a widening of login.
    - **The vault's redirect flow can't be the only connect path.** [`oauth.service.ts:68-71`](../packages/gateway/src/workflows/credentials/oauth.service.ts#L68-L71) throws when `clientSecretEnv` is unset, and a redirect grant needs a callback GitHub can reach. Shipping connect as redirect-only would make Themes B/E/F **unreachable on every real install** unless each user registered their own GitHub OAuth app and hand-pasted a secret into `~/.midnite/.env` — reintroducing exactly the friction the device flow removed for sign-in. So: **device grant is the default and the zero-config path; redirect is an operator opt-in** for hosted deployments. GitHub's device flow works for OAuth Apps with no client secret, which is what makes this possible; the connect app needs **Enable Device Flow** ticked at registration (the login app's did, and forgetting it is the classic failure).
    - Themes **C + D** need no GitHub connection at all — multi-repo projects and the cwd precedence fix are pure-local wins that land on a disconnected install regardless, so they're the safe floor if the connect work slips.
